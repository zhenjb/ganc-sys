### `internal/batch/builder.go` *(mới — thay file placeholder)*

```go
var ErrInvalidSettlementInputs = errors.New("batch: invalid settlement inputs")

type SettlementInputs struct {
    OldStateRoot        string
    NewStateRoot        string
    Deposit             types.DepositRecord
    Withdraw            types.WithdrawRequest
    Nullifier           string
    WithdrawAddressHash string
}

type SettlementUpdateBuilder struct { /* mu, seq */ }

func NewSettlementUpdateBuilder() *SettlementUpdateBuilder
func (b *SettlementUpdateBuilder) Build(in SettlementInputs) (types.SettlementUpdate, error)
func (b *SettlementUpdateBuilder) Seq() uint64
```

Pipeline validation trong `Build`:

1. `OldStateRoot` / `NewStateRoot` non-empty + `0x`-prefixed + non-empty sau strip.
2. `OldStateRoot != NewStateRoot` (chặn no-op batch nuốt batchId + nullifier).
3. `Deposit.{DepositID, Owner, Denom}` non-empty; `Amount` parse được như positive big.Int.
4. `Withdraw.{WithdrawID, Owner, Denom, Destination}` non-empty; `Amount` positive; `Nonce` non-negative.
5. `Nullifier` non-empty + `0x`-prefixed.
6. `WithdrawAddressHash` non-empty + `0x`-prefixed.
7. `Deposit.Denom == Withdraw.Denom` (MVP single-denom batch).
8. Re-derive `state.WithdrawAddressHash(Withdraw.Destination)` và assert bằng input — defense-in-depth, bắt drift `destination ↔ hash` trước khi gửi prover.

Output: `SettlementUpdate` với:
- `BatchID = "batch-N"` (N = `seq++` sau khi mọi validation pass).
- `DepositAmount` / `WithdrawAmount` đi qua `big.Int` → canonical string (`"01"` → `"1"`).
- Các field khác giữ nguyên byte từ record nguồn (vì STATE-03/04 đã trim sẵn).

## Hành vi đã chốt

### 1. Builder là *assembly*, không phải *orchestration*

STATE-08 KHÔNG gọi `ApplyDeposit` / `ApplyWithdrawal` / `NullifierFor` / `WithdrawAddressHash` thay caller. Caller chịu trách nhiệm thực thi STATE-03..07 theo đúng thứ tự và chuyển artifact vào `SettlementInputs`.

**Why:** mỗi STATE đã có owner rõ ràng (LocalState là state-machine, `NullifierFor`/`WithdrawAddressHash` là pure function). Gộp tất cả vào builder sẽ:

- Tạo hidden coupling: bug trong `ApplyWithdrawal` có thể manifest ở `batch.Build`.
- Khó test đơn nguyên (phải seed LocalState đầy đủ để test 1 validation rule).
- Khó tái sử dụng builder ở các path không cần off-chain mirror (vd. P4 nhận trực tiếp `SettlementUpdate` từ peer trong tương lai).

Pattern này song song với `WithdrawRequestBuilder` (STATE-04): builder = thuần dữ liệu + sequence id; mutator state riêng.

### 2. Re-derive `withdrawAddressHash` ngay trong `Build` (defense-in-depth)

Caller phải pass cả `Withdraw.Destination` lẫn `WithdrawAddressHash`. Builder gọi lại `state.WithdrawAddressHash(Destination)` và assert equality. Nếu mismatch → reject với sentinel.

**Why:**

- STATE-07 changenote điểm ra scenario: attacker rewrite `WithdrawAddress` giữa prover và chain → P1 verifier reject do hash mismatch. STATE-08 áp dụng cùng cơ chế ở off-chain pipeline: nếu code path nào đó (P4 backend, indexer) drift `destination` và `hash`, builder bắt trước khi gửi prover.
- Cost: 1 lần SHA-256 (≈microsecond), không cache.
- Failure mode được test `TestBuild_RejectsTamperedWithdrawAddressHash` cover.

### 3. Reject no-op batch (`oldRoot == newRoot`)

Một batch không thay đổi root vẫn sẽ tiêu thụ:
- 1 `batchId` (sequence không lùi).
- 1 nullifier (chain set `nullifierUsed`).
- 1 deposit (chain set `depositProcessed`).

→ Cho phép sẽ "burn" artifact mà không đem lại transition. Reject sớm, để caller fix logic.

### 4. Mixed-denom rejected (MVP single-denom)

ZK-04 (P2 circuit) hiện chỉ chứng minh `newBalance = oldBalance + depositAmount - withdrawAmount` với **một** account `(owner, denom)`. Batch trộn deposit `uusdc` + withdraw `uatom` sẽ làm constraint mất ý nghĩa.

**Why không gộp denom vào hash:** giữ rule explicit và rõ ràng để khi MVP mở rộng multi-denom, chỉ cần (i) đổi rule này (ii) cập nhật circuit. Hiện tại không có lý do để cho phép trộn.

### 5. Amount canonicalization qua `big.Int`

`"0100"` / `"100  "` / `"100"` → output `"100"`. Cùng pattern STATE-06 áp dụng cho `nonce`.

**Why:** public input order chốt trong Agreements là `[oldStateRoot, newStateRoot, depositAmount, withdrawAmount, withdrawAddressHash, nullifier]`. Nếu prover hash `"0100"` còn verifier hash `"100"` thì public input bytes khác nhau → proof reject. Canonical hoá tại STATE-08 đảm bảo hai bên thấy cùng byte.

### 6. BatchID auto-incremented, không truyền vào

Caller không được gán `BatchID` thủ công. Lý do:

- Tránh xung đột id giữa nhiều caller (race condition trong tương lai khi có nhiều endpoint cùng build batch).
- Giữ id sequencing local trong process (P4 có thể restart và reset → để P3 owner sequence riêng và persist ra ngoài nếu cần).
- MVP đơn giản: chuỗi tăng dần `batch-1, batch-2, ...`. Khi cần persist qua restart (production), thay implementation bằng `nextBatchID()` đọc/write từ store mà không phá API.

### 7. Sequence không advance khi `Build` lỗi

Test `TestBuild_FailureDoesNotIncrementSeq` khoá hợp đồng này. Implementation: increment `seq` **sau** mọi validation. Code path:

```go
// ... all validations ...
b.mu.Lock()
defer b.mu.Unlock()
b.seq++
return types.SettlementUpdate{BatchID: "batch-" + ..., ...}, nil
```

Hệ quả: nếu N lần đầu Build lỗi, lần thứ N+1 thành công vẫn nhận `batch-1`. Đây là behavior mong muốn — id `batch-1` luôn map sang batch đầu tiên thực sự được nominate.

### 8. Concurrency-safe

Builder dùng `sync.Mutex` quanh `seq++`. Test `TestBuild_ConcurrentBuildsAssignDistinctBatchIDs` chạy 16 goroutines song song và assert (a) không trùng id (b) `Seq()==16`.

**Why:** P4 thiết kế REST API multi-request; `POST /api/batch/build` có thể nhận đồng thời từ nhiều client. Builder phải an toàn.

## Hạn chế đã biết

1. **`BatchID` không persist qua restart**. MVP scope. Khi production hoá, đổi `seq` sang persisted counter trong cùng store với deposit queue. API không đổi.
2. **Một batch = 1 deposit + 1 withdraw**. Schema và circuit hiện tại fix shape này. Multi-tx-per-batch là future work; sẽ cần đổi `SettlementInputs` thành slice và bump circuit.
3. **Không check `Deposit.Processed`**. Builder không biết deposit đã được on-chain `depositProcessed=true` hay chưa. Nếu builder được gọi sau khi P1 đã accept proof cho `dep-1`, nó vẫn sản sinh batch — nhưng P1 sẽ reject do `depositProcessed[dep-1]==true`. Trách nhiệm idempotency thuộc về P1; STATE-08 là pure assembly. Có thể thêm guard tùy chọn (kiểm tra `LocalState.IsDepositApplied`) nếu thấy bug recurring.
4. **Không sign update**. Field `signature` không có trong schema chốt. Trust model MVP: relayer là honest (chỉ submit update do P3 phát).
5. **Re-derive chỉ cho `withdrawAddressHash`**. Không re-derive `nullifier` từ `(userSecret, nonce)` vì STATE-08 không nhận `userSecret` (giữ ra khỏi pipeline càng lâu càng tốt). Trade-off: nếu caller pass `nullifier` sai, builder không bắt được — sẽ bị P1 verifier reject. Có thể thêm `UserSecret` vào `SettlementInputs` nếu muốn defense-in-depth thêm, nhưng MVP chấp nhận trade-off để tránh leak secret xuống batch package.
