## Những gì đã đưa vào

### `internal/batch/witness.go` *(mới — thay file placeholder 1 dòng `package batch`)*

```go
var ErrInvalidWitnessInputs = errors.New("batch: invalid witness inputs")

type WitnessInputs struct {
    UserSecret string
    Settlement SettlementInputs  // reuse output từ STATE-08
    OldBalance string
    NewBalance string
    StatePath  []string           // optional, MVP để nil
}

type WitnessBuilder struct{}  // stateless

func NewWitnessBuilder() *WitnessBuilder
func (b *WitnessBuilder) Build(in WitnessInputs) (types.Witness, error)
```

Pipeline validation trong `Build`:

1. `UserSecret` non-empty sau `strings.TrimSpace`.
2. `Settlement.Withdraw.Nonce` parse non-negative `big.Int`.
3. `OldBalance` / `NewBalance` parse non-negative `big.Int`.
4. `Settlement.Deposit.Amount` / `Settlement.Withdraw.Amount` parse positive `big.Int` (belt-and-braces: STATE-08 đã check; gọi lại cho từng case test isolate `WitnessBuilder` không cần `SettlementUpdateBuilder` đi qua trước).
5. `Settlement.Deposit.Denom == Settlement.Withdraw.Denom` (single-denom invariant, mirror STATE-08).
6. **ZK-04 balance constraint**: `newBalance + withdrawAmount == oldBalance + depositAmount`.
7. **ZK-05 nullifier constraint** (defense-in-depth): re-derive `state.NullifierFor(secret, nonce)` và assert bằng `Settlement.Nullifier`.

Output: `types.Witness` với:
- `UserSecret` trim sạch (whitespace bị strip).
- `Nonce` / `OldBalance` / `NewBalance` canonical hoá qua `big.Int.String()` (`"01"` → `"1"`, `"0060"` → `"60"`).
- `StatePath` defensive copy khi non-empty, nil khi caller không pass.

## Hành vi đã chốt

### 1. WitnessBuilder reuse `SettlementInputs`, không trùng dữ liệu

`WitnessInputs.Settlement` là field của type `SettlementInputs` (cùng bundle đã pass STATE-08). Lý do:

- **Single source of truth.** Caller (P4 backend orchestration) đã có `SettlementInputs` để gọi `SettlementUpdateBuilder.Build`; truyền cùng bundle vào `WitnessBuilder.Build` đảm bảo update + witness không drift giá trị (denom, nonce, nullifier, address hash, amounts).
- **Tách secret khỏi `SettlementInputs`.** `UserSecret` là field RIÊNG trong `WitnessInputs`, không lẫn vào `SettlementInputs`. Hệ quả: `batch.SettlementUpdateBuilder` không bao giờ thấy secret — code path đẩy update lên prover/chain không thể vô tình leak.
- **Test isolation.** Test STATE-09 build trên `canonicalAlice(t)` (đã có) + 2 field thêm; không cần seed lại pipeline.

### 2. ZK-04 constraint là hard gate

`newBalance + withdrawAmount == oldBalance + depositAmount` được enforce trong builder.

**Why:**

- Witness sai → proof không generate được (circuit reject) hoặc generate xong nhưng public input mismatch → P1 verifier reject. Bất kể đường nào, mất 1 round-trip prover (đắt, ZK-09 đo benchmark hàng giây).
- Catch ngay STATE-09 → fail trong microsecond, log đầy đủ 4 con số để debug.
- Test `TestWitnessBuild_RejectsBalanceTransitionViolation` cover 3 cách break (newBal off-by-one ±, oldBal off-by-one).

**Edge case đã suy nghĩ:** nếu STATE-03/05 implement đúng thì constraint này KHÔNG BAO GIỜ vi phạm với artifact từ LocalState. Validation thừa cho happy path. Nhưng vẫn giữ vì:

- Caller có thể pass balance snapshot SAI (vd. lấy account của `mallory` thay vì `alice`, hoặc snapshot từ chain thay vì local mirror).
- Defense-in-depth chống refactor sau này: nếu ai đó break `AccountState.Debit` invariant `nonce++`, constraint balance vẫn bắt.

### 3. ZK-05 nullifier re-derive (defense-in-depth)

`state.NullifierFor(secret, nonce.String())` được gọi trong `Build`, so sánh với `Settlement.Nullifier`. Mismatch → reject.

**Why:**

- `Settlement.Nullifier` được pass vào `SettlementUpdateBuilder` từ STATE-06. Builder STATE-08 KHÔNG re-derive (vì không nhận secret — invariant security). STATE-09 là điểm duy nhất có CẢ secret VÀ nullifier → check ở đây mới có effect.
- Threat: caller có secret đúng nhưng nullifier sai (vd. cache stale, nonce off-by-one) → proof sai loop về P1 reject. Catch sớm tiết kiệm thời gian.
- Cost: 1 lần `SHA-256` (~microsecond). Domain tag bằng nhau với STATE-06 (`state.NullifierFor` là canonical entry point) → không có khả năng drift.

### 4. Canonical hoá scalar qua `big.Int`

`Nonce`, `OldBalance`, `NewBalance` đi qua `parseNonNegative(...).String()`. Cùng pattern STATE-06 áp dụng cho `nonce`, STATE-08 áp dụng cho `amount`.

**Why:** witness JSON là input cho prover. Prover hash từng field thành field element. Nếu prover hash `"0060"` và verifier (P1) hash `"60"` (re-derive từ chain), bytes khác nhau → public input khác nhau → proof reject. Canonical hoá tại nguồn (STATE-09) đảm bảo cả pipeline thấy cùng bytes.

`UserSecret` chỉ trim whitespace (không canonical hoá khác) vì secret là opaque bytes; chuẩn hoá thêm sẽ silently rewrite secret material.

### 5. StatePath defensive copy + omitempty

```go
var statePath []string
if len(in.StatePath) > 0 {
    statePath = append([]string(nil), in.StatePath...)
}
```

- **Defensive copy:** caller có thể mutate slice gốc sau Build (vd. reuse buffer). Witness phải immutable đối với caller. Test `TestWitnessBuild_StatePathDefensiveCopy` lock.
- **Nil khi empty:** `omitempty` trong JSON tag drop field. P2 prover (MVP) không có statePath → simpler payload. Khi ZK-06 lock final state model, generator sẽ populate; client/JSON decoder không cần thay đổi.

### 6. WitnessBuilder stateless

Không có `seq`, không có counter. Witness không cần monotonic id (BatchID đã do `SettlementUpdate` mang). Concurrency-safe by construction.

Test `TestWitnessBuild_Concurrent` lock invariant: 16 goroutines build cùng input → output identical, không data race (race detector clean).

### 7. KHÔNG bao gồm các field thuộc về `SettlementUpdate`

Witness CHỈ chứa private inputs. Public inputs (oldRoot, newRoot, amounts, addressHash, nullifier) nằm trong `SettlementUpdate` và sẽ được STATE-10 build thành `public_inputs.json` ordered list.

**Why:** prover đọc 2 file: `settlement_update_batch_1.json` (public) + `witness_batch_1.json` (private). Tách hai loại input giảm rủi ro leak secret vào artifact public.

## Hạn chế đã biết

1. **StatePath là nil/empty trong MVP.** ZK-06 dùng simplified state model — chỉ chứng minh root update cho một account `(owner, denom)` đơn lẻ. Khi mở rộng multi-account hoặc merkle-style commitment, generator + builder phải populate path; consumer (P2) cần chấp nhận shape mới.
2. **OldBalance/NewBalance phải pass bằng tay.** Builder không reach vào `LocalState` để extract balance — giữ stateless. Trade-off: caller (generator hoặc P4 orchestration) phải remember capture `Account().Balance` đúng thời điểm. Đã có test cover edge case capture sai (off-by-one).
3. **UserSecret là plain string trong test vector.** `testvectors/alice_100_40/witness_batch_1.json` chứa `"alice_secret"` — demo only. Không bao giờ commit witness với secret thật. Production sẽ generate witness ephemeral trên prover host và xoá sau khi proof ra.
4. **Không sign witness.** Trust model: prover host được tin tưởng. Nếu mở rộng prover thành multi-party hoặc remote service, cần authenticated channel; out of MVP scope.
5. **Không re-derive `withdrawAddressHash` ở đây.** STATE-08 đã re-derive một lần khi build update. Re-derive lần 2 ở witness builder là thừa (cùng input `Settlement.Withdraw.Destination`). Nếu STATE-08 đã pass thì hash bằng nhau.
