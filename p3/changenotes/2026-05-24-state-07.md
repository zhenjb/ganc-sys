## Hành vi đã chốt

### 1. Hash là SHA-256 với domain tag versioned RIÊNG cho address

ZK-02 chưa lock Poseidon/MiMC cuối cùng. STATE-07 dùng SHA-256 (đã có sẵn trong `pkg/hash`) như placeholder. Quy trình chuyển hash song song với STATE-06:

1. Khi ZK-02 lock circuit hash, thay implementation trong `WithdrawAddressHash`.
2. Bump `withdrawAddressDomainTag` từ `"v0"` → `"v1"` trong cùng commit.
3. Chạy `go run ./p3/script-test/gen_state_vectors` để regenerate `withdraw_address_hash_wd_1.json`.
4. Test `TestWithdrawAddressHash_CanonicalAliceVector` sẽ fail → cập nhật constant `canonicalWithdrawAddressHash` cùng commit.
5. Notify P2 / P1 / P4.

**Why domain tag tách rời `nullifierDomainTag`:** mặc dù 2 derivation hiện cùng SHA-256, để chúng dùng chung tag sẽ mở cửa cho attacker chọn `destination` có hình dạng `"secret|nonce"` để tạo ra hash trùng nullifier (cross-domain forgery). Giữ 2 constant riêng rẽ — chi phí cognitive load 1 dòng để khoá an toàn về sau. Test `TestWithdrawAddressHash_DomainSeparatedFromNullifier` cover.

### 2. API trả `(string, error)` chứ không panic

Lý do như STATE-06: input từ HTTP body. Trả error → P4 map sang 400.

### 3. Canonicalization chỉ là `TrimSpace`

Không lowercase, không bech32-parse. Lý do:

- `WithdrawRequestBuilder.Build` (STATE-04) đã `TrimSpace(Destination)` trước khi gắn vào `WithdrawRequest`. STATE-07 chỉ cần cùng quy ước để output khớp.
- Lowercasing có thể "cứu" được mixed-case input nhưng cũng có thể "phá" được địa chỉ tương lai phân biệt hoa-thường (vd. EVM checksummed address). Không dám commit vào MVP.
- Bech32 validation là việc của `x/bank.SendCoinsFromModuleToAccount` ở thời điểm claim (P1 ONCHAIN-10). STATE-07 chỉ cần đảm bảo bytes prover hash = bytes chain hash khi verify proof.

Test `TestWithdrawAddressHash_MatchesWithdrawRequestDestination` khoá hợp đồng này: nếu STATE-04 sau này đổi canonicalization, test fail trước khi prover/verifier bị silent drift.

### 4. Field separator '|' bắt buộc

Mặc dù hiện hash chỉ có 1 field (`destination`), separator '|' được giữ vì:

- Đồng nhất với pattern STATE-06 (`H(domain | secret | nonce)`), giảm cognitive load khi P2 implement circuit.
- Nếu sau này thêm field (vd. `chainId` để cross-chain replay protection), không bị collapse với input cũ.

### 5. Không validate bech32 / prefix

`destination` là opaque bytes — STATE-07 chỉ guarantee non-empty sau trim. Validate format là việc của:

- P5 UI (định hướng user nhập đúng).
- P4 backend (sanitize trước khi forward).
- P1 chain (rejected tại `x/bank` nếu sai).

Tránh lockin sai chỗ; nếu MVP đổi sang Stargate IBC address, address-hash code không phải đụng.

### 6. Không có persistent storage

Function pure — không state, không mutex, không I/O. Caller (P3 batch builder STATE-08, P4 endpoint) chịu trách nhiệm cache nếu cần.

## Hạn chế đã biết

1. **Hash placeholder không zk-friendly**: SHA-256 không phải Poseidon. Final defense bắt buộc phải swap. Đã document quy trình bump version.
2. **Không tự normalize case**: nếu UI gửi `"Cosmos1Alice"` thay vì `"cosmos1alice"`, hash khác → proof khớp với một địa chỉ khác → `x/bank` reject claim. Trách nhiệm UI/P4 sanitize.
3. **Không cover IBC / cross-chain destination**: hash chỉ là `H(domain | destination)` đơn lẻ. Nếu MVP mở rộng sang IBC, cần thêm `chainId` vào input và bump `v0 → v1`.
